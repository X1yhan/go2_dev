go2_dev · 架构说明 · 可视化版

为什么这么分层 一张能看懂的图：现在的代码长什么样、为什么它是个问题、拆成什么样、为什么先拆文件而不是先拆节点。

ROS 2 已经替我们分好了层——节点是进程边界，msg 是数据契约，launch 是组合方式。 所以在这个项目里，「架构」不是「要不要拆节点」，而是三个能直接检查的问题：
① 一个节点能不能用一句话说清它做什么？
② import 关系会不会跨层？
③ 话题名和帧名有没有写在纸上？
01

代价 1

改色阈值要连 MoveIt

检测逻辑只依赖 numpy 数组，但因为和规划写在同一个类里，它永远拿不到一个「只加载 cv2」的运行环境。

代价 2

最关键的那句话没法单测

「给一张图 + 深度，输出物体在 base_link 下的位姿」——这句话是这个项目真正要验证的东西，却需要一个活着的 Gazebo 和一个活着的 move_group 才能跑。

代价 3

想复用它只能起子进程

语言层要「扫一眼桌上有什么」，只能 subprocess.Popen 起一个新进程，拿回一个退出码。所有失败细节都留在日志里。

02

最便宜能修的一处：一行 import 打穿了四层

语言层需要一张「物体尺寸表」OBJECTS。为了它，写了这么一行——就在 arm_bench_language.py:21： 

# arm_bench_language.py:21 —— 本来只想拿一张尺寸表
from arm_bench_visual_grasp import OBJECTS

这一行把整条依赖链拖进了「中文语言解析」这个进程： cv2numpycv_bridgetf2_roscontrol_msgsmoveit_msgs
于是「语言解析」这个纯逻辑，永远无法脱离 ROS + MoveIt + OpenCV 运行——它连 import 都做不到。

实测代价
· 语言层不能单测
· 换前端要重装整条工具链
· 铁律 1 被静默违反
修它只要挪一张字典
这一处已经修了
那张字典现在在 arm_bench/objects.py（78 行，纯 stdlib，没有 import）。 语言层只 from arm_bench.objects import LABEL_CN，铁律 1 的 grep 从「有输出」变成「无输出」。 顺带的好处：parse_command('抓红球,放到黄盒子上') 现在可以在一台没装 ROS 的机器上跑。

为什么是这五层，而不是别的切法？因为它们的变化频率不同： L1 换硬件才变、L2 换相机/换检测器才变、L3 物体增加才变、L4 动作定义才变、L5 换交互方式才变。 变化频率不同的东西放在同一个文件里，每次改动都得重新理解整个文件——这就是那 1040 行真正的成本。

04

三条铁律，用 grep 检查

「分层」如果不写成能自动检查的规则，三个月后一定会被一句「先这样，回头再改」吃掉。 下面三条每一条都只要一行 grep，右边是今天跑出来的真实结果。

✓

铁律 1 · L5 不许直接或间接依赖 MoveIt / OpenCV

grep -nE "^\s*(from|import)\s+(moveit_msgs|cv2|geometry_msgs)" \
  ros2_ws/src/go2_description/scripts/arm_bench_language.py
# 直接 import：干净（无输出）
# 改造前：第 21 行 from arm_bench_visual_grasp import OBJECTS
#         间接把 cv2 / numpy / cv_bridge / moveit_msgs 全拉进来 → 违反
# 改造后：OBJECTS 搬到 arm_bench/objects.py，这行已删
#         现在整条链路只剩 arm_bench.language + arm_bench.objects → 无输出
已修
✓

铁律 2 · L2 感知层不许 import moveit_msgs

grep -rln "moveit_msgs" \
  ros2_ws/src/go2_description/scripts/arm_bench_object_detector.py \
  ros2_ws/src/go2_description/scripts/arm_bench/{detection,vision}.py \
  ros2_ws/src/go2_vision/scripts/
# 无输出（拆出来的 detection.py / vision.py 也没破这条）

✓

这条改写过了。原来是「只有 L4 可以 import moveit_msgs」——但 L3 的职责就是往 MoveIt 下发 planning scene，它必须是 moveit_msgs。原写法自相矛盾，拆到 L3 时才暴露出来。 规则改成「只允许 L3 与 L4，且文件名写死在检查脚本里」。

05

什么时候才该拆成节点

这是本文里最重要的一条工程判断：分层 ≠ 拆节点。 节点是进程，拆一个节点就多一次序列化、多一个崩溃点、多一个要单独起的终端。所以拿三个问题卡一下：

Q1
需要独立频率吗？
→
Q2
需要崩溃隔离吗？
→
Q3
需要被别的进程单独起吗？
→
三个都是「否」
别拆
任一为「是」→ 才考虑拆节点。按这个判据：pick / place 不该拆。 它本来就是「调一次、等结果」，拆成 action server 只会把这句话变成 goal / feedback / cancel 一套编排，凭空多出失败点。
候选独立频率崩溃隔离单独起结论理由
检测器是 · 30 Hz是 · cv2 会挂是 · RS 要看节点已经是，保持
场景发布是 · 物体动了就发否是 · --interactive节点已经是，保持
scan否 · 一次性否是 · scan_only暂不拆用参数表达，够用
pick / place否 · 一次性动作否否不拆拆了只增加编排成本
语言否 · 交互否否不拆本来就是一个前端
06

  • /arm/camera/depth_image

  • base_frame: base_link

09

明确不做的事

写清「不做什么」比写「要做什么」更能防止半年后的自己被绕回去。

不做理由
拆纯转发节点每个节点都是一次序列化 + 一次调度；转发节点只增加延迟和故障点，不增加隔离
引入行为树（py_trees）现在是「一次抓取」的线性流程。行为树会把现在的线性 REPL 变成 800 行的树。等出现多任务并发/抢占/恢复需求再说
现在就统一 vision_sim 与 go2_vision一个是仿真验证环境、一个是狗载真机管线。合并收益要等两边话题稳定后再评估。先写清结论，别动代码
为分层而分层（每层一个 msg）层间传递用 dataclass 就够；只有跨进程才需要 msg

ROS 已经把「层」给你了。你缺的不是分层，是「层写在哪」。

把隐含的边界变成显式的、能 grep 的、写在纸上的边界——收益远大于改代码结构。

而每一步都要守住同一件事：动完之后，仍然能用一条命令抓起那颗红球。
